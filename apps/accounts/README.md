# Accounts service

A Canton account that a person holds with a key of their own, made and used from a web page. The account is an external party: its Ed25519 key is made by its owner (the page derives it from one wallet signature), the party is hosted on the operator's participant, and only that key can sign for it. This service sits between the page and the participant's JSON Ledger API (Canton 3.7). It holds a Ledger API token and never a key of any account. One Python file; the standard library and the `cryptography` package, which a deployment must install (it checks the signatures). The service has a pure-Python check for when the package is missing (about 5 ms for each signature), and then logs a loud warning at start: use it for tests only. The tests (`unittest`, which `pytest` collects too) run against a fake Ledger API, and one test runs against the real, pinned Canton. The service is deployed on DevNet (commit c350f87, 8 November 2026) behind the explorer's Bridge page.

```
LEDGER_TOKEN=<token> accounts.py --ledger-url http://participant:7575 --user-id <ledger user of the token> --state-file accounts.jsonl [--listen 127.0.0.1:8081]
```

The token comes from `LEDGER_TOKEN` or `--token-file` (read again for each call, so a rotated token is picked up), never from an argument. `--user-id` is the Ledger API user of that token. The public endpoint must run behind a reverse proxy; the service limits each client itself (below), and `--client-ip-header X-Forwarded-For` makes it take the client's address from that header instead of the proxy's: the `--trusted-proxies N`-th entry from the right (default 1, the entry the nearest proxy wrote), and only when the TCP peer is one of `--trusted-proxy-addresses` (comma-separated addresses or networks, default `127.0.0.1,::1`). From any other peer the header is ignored and the peer's address is the client; so is a header with fewer than N entries.

**The reverse proxy must pass the path unchanged.** An account signs the path of its request (below), and the service checks it against the path it receives. Use `proxy_pass http://127.0.0.1:8081;` with no URI part, and no prefix stripping or rewriting; if the path changes on the way, every account signature fails with a 401.

## Before you expose it

- `cryptography` is installed, and the log has no slow-verify warning at start.
- `--chain-parties` (or the four `--chain-*` options) is set; without it the chain's creates are refused.
- The reverse proxy uses `proxy_pass http://127.0.0.1:8081;` with no URI part and no prefix, so the path reaches the service unchanged.
- `--client-ip-header`, `--trusted-proxies` and `--trusted-proxy-addresses` match the proxy chain: the header is read only from a trusted peer, and the client is the entry the nearest proxy wrote.
- A service that passes its own `--allow` lists `'#canton-zk-evm:Zk.Chain:RedeemRequest#Archive'` (an exercise, so no `--open-limit`) as well as the three take-back entries (`Allocation_Withdraw`, `DepositRequest#Archive`, `TransferInstruction_Withdraw`, the last as `'#splice-api-token-transfer-instruction-v1:Splice.Api.Token.TransferInstructionV1:TransferInstruction#TransferInstruction_Withdraw'`, an exercise, so no `--open-limit`); without it, every removal of a redeem request is a 403, and a page that gives a move up treats that as permanent. Check the running service's command line, not only the run script.
- The participant's `max-self-allocated-parties` and `max-rights-per-user` are sized for the number of accounts the service may hold (both default to a low number, and `--accounts-per-day-total` only bounds a day).
- One copy of the service runs, with `--state-file` on persistent disk: the pending entries, the limits and the replay memory are in its memory.

## Endpoints

Every answer is JSON; an error is `{"error": "..."}` (a 409 is `{"error": "<code>", "message": "..."}`, below) with 400 (a bad request), 401 (no signature of the account's, one that is stale or, for a request that changes something, used before, or one that is not the account's), 403 (a command that is not on the list, or names other parties), 404 (no such account, topology or prepared transaction), 409 (a conflict with what the account has or has waiting: it always has a code, below), 422 (the participant refused it: `code` and `detail` carry its answer), 429 (a limit, with `Retry-After`), 502 (the participant, a token registry or the validator's wallet could not be reached, or refused the service's own login; no detail is given, only a registry's HTTP status as `registryStatus`) or 500. Binary values are base64.

**Conflicts (409).** A 409 answers `{"error": "<code>", "message": "<plain words>"}`: the code is stable, so a client acts on it and never on the message, which a person may read and which may change. Every other error keeps `{"error": "<message>"}`. The codes, one for each case:

| Code | When | What a client does |
|---|---|---|
| `already_accepted` | `prepare` or `execute` of a standing acceptance (a `WithdrawalAcceptance`, a `TwinAcceptance`: any allowed create whose template name ends in `Acceptance`) for an account that has one open already | The acceptance is there: carry on. `GET /accounts/v1/open/{party}` gives its contract id |
| `too_many_open` | `prepare` or `execute` of another limited create (a `DepositRequest`) when the account has its limit open already (`--open-deposit-requests`, `--open-limit`) | Wait until one is spent |
| `waiting_for_signature` | `prepare` of a limited create when the account has a prepared transaction of that template waiting for its signature | Execute that one, or wait for it to expire (10 minutes) |
| `not_yet` | `prepare` of `Allocation_Withdraw` or of the `DepositRequest`'s `Archive` while the builder can still settle the deposit (below) | Wait until the allocation's settle-before time has passed, then ask again |
| `account_key_unknown` | A request about an account the participant has but whose key this service does not (the state file lost its line) | Register it again: `topology` and `allocate` with the same key |

| `GET /healthz` | | `{"ok", "accounts"}`; `ok` is false when the participant does not answer; the answer is kept for 5 seconds |

The party id is `rome::<fingerprint of the key>` (the name before the fingerprint is `--party-hint`, default `rome`; the page's `VITE_PARTY_HINT` must be the same), so the same key is always the same account and `allocate` for it twice makes nothing the second time. The service answers for the accounts it allocated only (it keeps them in `--state-file`, one JSON line each, so keep that file): `prepare`, `execute` and `holdings` for another party are 404.

**Proof of the account's key.** `prepare`, `execute`, `holdings`, `allocations`, `open`, `transfers`, the registry relay and the faucet are about one account, and each request carries that account's signature in the header `X-Account-Signature: <unix-seconds>.<base64 signature>`. The signature is Ed25519, made with the account's key (the one it was allocated from) over the UTF-8 string

```
accounts-v1\n<METHOD>\n<PATH>\n<hex sha256 of the body>\n<unix-seconds>
```

that is, five lines joined by a line feed (`\n`, none at the end): the text `accounts-v1`; the method in capitals (`GET` or `POST`); the path as sent, without a query (for example `/accounts/v1/holdings/rome::1220...`); the sha256 of the request body's bytes in lowercase hex (of the empty string for a `GET`; the body is signed exactly as it is sent); and the same unix seconds as in the header. The service verifies it with the account's stored public key, accepts it only within 60 seconds of its own clock, and accepts each `(account, seconds, signature)` of a request that changes something (`POST`, and `PUT` or `DELETE` where there are any) once, so a replay is refused: a request that repeats an earlier one (same method, path and body) needs another second or a new body. **A signed `GET` is not remembered.** `holdings`, `allocations`, `open` and `transfers` only read, so two identical signed reads in the same second (two tabs, or two reads on one page) both answer 200; they keep the signature check, the 60-second window and the per-account rate (`--requests-per-account-minute`). The only thing a repeated read allows is the same read again within the window. A repeated read counts against the same per-account rate as the writes. The registry relay is a `POST` (its body carries the registry's request), so it stays under the replay memory. The page also sends one request for identical signed reads that are in flight together. A missing, malformed, stale, used (a `POST` repeated) or wrong signature is a 401, and nothing reaches the participant. `topology`, `allocate`, `healthz` and the public registry relay (below) need none.

**What an account may sign.** `prepare` takes one command, a `CreateCommand` or an `ExerciseCommand` (not `CreateAndExercise` or by key), and only if it is on the list. An entry is `#package:Module:Entity` (a create of that template) or `#package:Module:Entity#Choice` (an exercise of that choice, on a template or an interface). The package is named, never its id, so a command cannot step round the list by its package id. The built-in list is the chain package's `WithdrawalAcceptance` and `DepositRequest` creates, the token standard's `AllocationFactory_Allocate`, `TransferFactory_Transfer` and `TransferInstruction_Accept`, the standard's `TransferInstruction_Withdraw` (an account takes back a transfer it sent that nobody accepted), two choices that let an account take back a deposit that cannot settle: the standard's `Allocation_Withdraw` and the `DepositRequest`'s `Archive`, and the `RedeemRequest`'s `Archive`, with which an account removes a redeem request of its own. All four are exercises, so no open limit applies to them. `prepare` checks them against the ledger: a `TransferInstruction_Withdraw` is accepted only on a transfer waiting for its receiver whose sender is the account (404 for any other: an offer made to the account is its receiver's to accept, not its to withdraw), at any time, a lapsed offer included, since that is the one the sender has to take back (the read that checks it is not capped, so a flood of offers made to the account cannot hide its own); an `Allocation_Withdraw` is accepted only on an allocation the account itself sent, and only once its settle-before time is past by 60 seconds (`TAKE_BACK_MARGIN`: Canton's default record-time tolerance, so that a ledger that still takes an `Advance` stamped just before the time has taken it by then; the builder leaves a deposit out of every block from 5 minutes before the time, so the withdraw cannot make a block's advance fail); an `Archive` only on the account's own open `DepositRequest` whose allocation is gone or past that time (an allocation missing from the account's list counts as gone only when the participant's own events for that contract show it archived or unknown). Before then the answer is a 409 `not_yet`. A redeem request locks nothing, so its `Archive` is accepted at any time on the account's own open `RedeemRequest` (404 for any other). A deployment that passes `--allow` must list these entries to offer this: a service started with its own list before the `RedeemRequest`'s `Archive` existed answers 403 to every removal of a redeem request until `--allow '#canton-zk-evm:Zk.Chain:RedeemRequest#Archive'` is added (an exercise, so no `--open-limit`), and the same holds for the three take-back entries. After changing the list, check the running service's command line. `--allow` (repeat it) replaces the list, for example to add the twin package's acceptance and redeem request. `execute` runs only a transaction that this service prepared for that party in the last ten minutes (it keeps the hash of what it prepared, in memory), so the list holds for execute too: a client cannot prepare elsewhere and send the result here. Because that memory is the service's, run one copy.

## Token registries and the DevNet faucet

**Registry relay.** The page builds a Canton Coin allocation (a deposit) and accepts an incoming transfer with the choice contexts of the instrument's token registry (CIP-0056's off-ledger API), and the Canton Coin registry, the validator's scan proxy, can be reached from the service's machine only. So the service relays, read-only, for each `--registry ADMIN=URL` (repeat; `ADMIN` is the instrument admin's party id, `URL` the root of the registry's API, for Canton Coin the validator's `.../api/validator/v0/scan-proxy`): `allocation-factory` goes to `<URL>/registry/allocation-instruction/v1/allocation-factory`, `transfer-factory` (the factory of a transfer the account sends) to `<URL>/registry/transfer-instruction/v1/transfer-factory`, `accept-context` to `<URL>/registry/transfer-instruction/v1/{cid}/choice-contexts/accept`, `transfer-instruction/{cid}/withdraw-context` to `<URL>/registry/transfer-instruction/v1/{cid}/choice-contexts/withdraw`, and `allocation/{cid}/withdraw-context` to `<URL>/registry/allocations/v1/{cid}/choice-contexts/withdraw`, with the request body (less `party`) and the answer passed through. `--registry-token-file ADMIN=FILE` names the file with the bearer token that registry wants, read again for each request, never logged; the file must be mode 0600 or stricter (the service refuses to start when group or others can read it). The registry is trusted for nothing: its URL is https, or a server on this machine (`localhost`, `127.0.0.1`, `[::1]`, or a name under `.localhost` whose addresses are all loopback, checked at start), and over http the connected peer is checked again on every request, before anything is sent; a redirect is not followed (a status other than 200 is a 502); the answer is read to at most 1 MiB, and the whole call (the connect and the read together) takes at most 15 seconds, counted from before the connect; the answer must be a JSON object; a request is at most 64 KiB. Each call counts against the account's `--requests-per-account-minute`. An admin without a `--registry` is a 404. To let accounts send twins, run it with `--registry <gateway party>=<the twin registry service's URL>` as well (`apps/twin/registry` serves the transfer factory; a twin transfer completes at once, so `transferKind` is `direct` and there is no accept-context for it); for Canton Coin it is the validator's scan proxy, as above. The built-in allow list holds `AllocationFactory_Allocate`, `TransferFactory_Transfer`, `TransferInstruction_Accept`, `TransferInstruction_Withdraw` and `Allocation_Withdraw`, which these contexts are for. The transfer factory has the same limits, timeouts, answer size and checks as the others (it is the same relay), and nothing about a transfer is checked by the service itself: the account signs its own transfer, the page holds the prepared transaction to what the person typed (`explorer/src/bridge/canton/sign.ts`), and the registry's choice does the rest. `TransferInstruction_Reject` is not on the built-in list: the page lets an account send, accept, and take back its own unaccepted sends, and nothing more. A deployment that passes `--allow` must list `TransferInstruction_Withdraw` to offer Take back (an exercise, so no `--open-limit`): without it every take back is a 403.

**The faucet (DevNet only).** `--faucet-amount N` (off when not given) makes the validator's own party send `N` Canton Coin to an account that asks, through the validator's wallet API: `POST <--faucet-url>/v0/wallet/token-standard/transfers` (`--faucet-url` is the validator API root, such as `https://validator/api/validator`; https, or a server on this machine) with `{"receiver_party_id", "amount", "description", "expires_at", "tracking_id"}`, reading `output` of its answer (Splice 0.10.0's `wallet-internal.yaml`, `createTokenStandardTransfer`): `{transfer_instruction_cid}` is a pending offer, `{receiver_holding_cids: [...]}` a completed transfer, anything else a 502. The token for that API is in `--faucet-token-file`, read again for each grant and never printed. **It is the validator's admin-level token, so the faucet is for DevNet only: never set it on a service whose validator holds value. The token file must be mode 0600 (the service refuses to start otherwise), and it is the one thing on this machine that can spend the validator's coins.** An account gets one grant a day, so does a client (an IPv4 address, an IPv6 /48), and `--faucet-per-day` (200) is the day's total, all accounts together (429 over any of them, with `Retry-After`). A grant counts when it is asked for, so one that fails still counts, with one exception: a failure before anything was sent to the wallet (the token file could not be read, the connection could not be made, or its peer is not this machine) cannot have made a transfer, so the account's, the client's and the day's allowance are given back. A failure after the request was written (a timeout, an answer that is not a success, a broken connection) is unknown, and it counts. When the transfer is an offer, the answer is `{"transferInstructionCid"}`: the page gets the accept context from `accept-context` above and prepares `TransferInstruction_Accept`; with a preapproval the answer is `{"completed": true}`.

**Public registry relay.** A person who connects a Canton wallet of their own has a party this service did not make, so it can neither find the party nor check a signature of its key. `POST /accounts/v1/public-registry/{admin}/{suffix}` gives such a wallet the same read-only registry calls as the relay above, to the same `--registry` for `{admin}`, with the same checks on the registry (https or this machine, no redirect, at most 1 MiB back, 15 seconds, a JSON object) and the same 64 KiB cap on the request. It needs no account and no signature, so nothing about an account is checked or remembered: the replay memory does not see it (two identical requests both answer) and the per-account rate does not count it. The body goes on exactly as it came, `party` included if there is one; no body at all is an empty request, and a body that is JSON but not an object is a 400. What limits it is the per-client rate `--public-registry-requests-per-minute` (30, per IPv4 address or IPv6 /64) and a ceiling over all clients together, `--public-registry-requests-per-minute-total` (600), on top of `--requests-per-minute` and `--requests-per-network-minute`, which every request counts. Everything it reaches is what the registry already answers to anyone; the service adds the bearer token for the registry and never returns it. The reverse proxy in front of the service passes the whole `/accounts/v1/` prefix, so it needs no change.

## What the service's user needs

The participant user of the token (`--user-id`) holds **no right of its own**. `allocate` passes the user id to the participant's external-party allocation, which gives that user `CanActAs` for the new party in the same call; the endpoint accepts the user's own token for that (the authenticated user may name itself), so the service needs no `ParticipantAdmin` and no `IdentityProviderAdmin`, and cannot grant itself or anyone else anything. `CanActAs` for the party implies reading as it and executing as it, which is all `prepare` (reads as the party), `execute` (acts or executes as the party) and `holdings` (reads as the party) ask for. It does not let the service act for an external party without that party's signature: the participant holds no key of the party. The integration test checks that the user ends with a right on the new party and no other right.

The participant must let a user without an admin right allocate parties for itself: `canton.participants.<name>.ledger-api.party-management-service.max-self-allocated-parties` (0 by default, which refuses the allocation with "User quota of party allocations exhausted"). Set it to the number of accounts the service may hold: it counts the user's rights on parties, so it is the cap on accounts, and the participant's `max-rights-per-user` (1000 by default) must be at least as high. Raise both as the accounts grow; `--accounts-per-day-total` keeps the new accounts of a day, whatever clients do, within what these two settings leave.

**Which parties the service holds.** The ledger user's own rights are the truth: the service reads `GET /v2/users/{userId}/rights` (its `CanActAs` rights) at start and again when a party is missed (at most every 5 seconds). The state file keeps each account's public key, and it can lose a line (a write cut short: a last line without a newline is ignored, and the next line starts on a new one). A party that is in the rights but not in the file is held with its key unknown. The Ledger API does not give a party's key (its party details carry none, and it has no topology read), so `prepare`, `execute` and `holdings` for it answer 409 "register it again". The owner's page asks for `topology` and `allocate` with the same key as before: the key's signature of the multi-hash proves it, and the service writes the line again (`{"party", "created": false, "restored": true}`) without asking the participant to allocate anything.

## Limits

Per client: `--accounts-per-day` (3) allocations that make an account in 24 hours, and `--requests-per-minute` (60) requests of any kind, and for the public registry relay `--public-registry-requests-per-minute` (30) requests. A client is an IPv4 address, or an IPv6 /64 (one subscriber holds a whole /64); the caps on what waits for a signature (below) count an IPv6 client by its /48. All clients together: `--public-registry-requests-per-minute-total` (600) public registry relay requests in a minute, and `--accounts-per-day-total` (200) new accounts in 24 hours. Each account is a party and a right of the ledger user, and the participant's quotas for them are finite, so this cap is what protects them from a flood of new accounts. Two more rates sit over these: `--requests-per-account-minute` (30) for `prepare`, `execute`, `holdings`, `allocations`, `open`, `transfers`, the registry relay and the faucet together, counted per account once its signature has verified (so naming an account cannot use up its rate), and `--requests-per-network-minute` (300) per IPv4 address or IPv6 /48, since a /48 holds many /64s. A body is at most 512 KiB. The faucet's limits are above. The service makes no account from a key that is not signed for: it checks the signature over the topology itself, and the participant checks it again. All limits are in memory.

**Creates name observers.** A `WithdrawalAcceptance` or `DepositRequest` is seen by the chain's parties, so `prepare` refuses (403) one whose `operator`, `confirmer`, `gateway` or `builder` is not the chain's, and any create that names a party that is neither the account nor one of the chain's. Name the chain's parties with `--chain-parties <json file>` (`{"operator": ..., "confirmer": ..., "gateway": ..., "builder": ...}`) or `--chain-operator`, `--chain-confirmer`, `--chain-gateway`, `--chain-builder`; without them these creates are refused. An account may have one open `WithdrawalAcceptance` and `--open-deposit-requests` (3) open `DepositRequest`s: the service reads the account's own active contracts and answers 409 over that, at prepare and again at execute. For such a template the check and the send are one step per account (a lock is held until the participant has committed), and an account with a transaction of that template waiting for its signature may not prepare another (409). In a create, `label` and `ref` are at most 128 characters and the whole of `createArguments` at most 2 KiB as JSON (400); contract ids and party ids are not capped. A create that has no open limit (`=none`) may name the account alone as a party. `prepare` sets the transaction's `maxRecordTime` to its own time plus the ten minutes it may wait for its signature and 30 seconds, so the participant refuses to record it later. An execute that got no answer from the participant (a timeout or a 5xx) counts as open for that account and template until then, since the transaction may still commit. The limits fail closed: the service does not start when an allowed create has no limit. Give one for each create added with `--allow` as `--open-limit '#package:Module:Entity=N'` (repeat it), or `=none` for a create that names no other party.

**Traffic.** Each execute and each allocation counts against a budget for 24 hours (429 over it): `--executes-per-account-day` (50), `--executes-per-client-day` (200) and `--executes-per-day` (2000, all clients). The participant's cost estimate of a prepared transaction (`costEstimation.totalTrafficCostEstimation`) must be at most `--max-transaction-traffic` (200000; a transaction with no estimate is refused with 502), and the estimates of the executes count against `--traffic-per-day` (50000000). The budgets are checked together and charged together: a request over one of them (429) charges none, and its prepared transaction stays for a later try. A prepared transaction otherwise has one attempt to execute: its entry is removed before anything is sent, so a refusal by the participant means preparing again. The service checks the account's Ed25519 signature of the prepared transaction's hash itself (`ed25519.py`, RFC 8032) before it asks the participant; a wrong one is a 401 and costs the participant nothing. A client (an IPv6 /48) with 10 failed signature checks in a minute is answered 429 without further checks until the minute is over; failures are not counted per account, as anyone can name an account. A key that is not of prime order (a small-order key, with `[8]A` the identity, or a mixed-order one, with `[L]A` not the identity) is refused at `topology`. The signature is sent with format `SIGNATURE_FORMAT_RAW`: the pinned Canton's OpenAPI spec (3.7.2, as 3.7.1) leaves the format a free string and names no other value.

**What waits for a signature.** At most `--max-pending-topologies` (2000) topologies and `--max-pending-prepared` (5000) prepared transactions, and `--max-pending-per-client` (10) of each per client address (503 over it, and before the participant is asked anything); an account has at most `--max-pending-per-account` (5) prepared transactions waiting. A key has one topology blob while it lives: asking again returns it and does not reach the participant (nor is the key checked again).

## The protocol version

The topology transactions are those of the synchronizer's own protocol version, unless `--topology-protocol-version N` asks for those of an older one (the participant's `generate-topology` takes `protocolVersion`; on a synchronizer of version 37, 36 is admitted). The service passes the transactions to `allocate` as they are, so it works on a synchronizer of version 36 and of 37; the integration test runs on the one `PINS` names. `--synchronizer-id` names the synchronizer to make accounts on; by default it is the one the participant is connected to (and it is an error if there are several).

## Tests

```
python3 -m unittest discover -s apps/accounts/tests -p 'test_*.py' -v     # a fake Ledger API, a fake registry and a fake wallet
apps/accounts/tests/integration.sh                                        # the pinned Canton; needs Java 21 and openssl 3
```

The second starts Canton as `tests/canton_external.sh` does, sets Ostia's chain up on it, makes a Ledger API user with no right, and runs the service with that user's token. `integration.py` makes an Ed25519 key with `openssl` (the repo has no crypto library, and the service needs none: it never signs), signs each account-scoped request with it as above (and sends one without a signature, which is a 401), allocates an external party from it, prepares and signs the creation of a `WithdrawalAcceptance` of the chain package, executes it, reads the contract back as an observer, and lists the holdings. It then gives the account a holding of the test token (a party on the participant sends it, the account's key accepts it), and has the key make an allocation, a `DepositRequest` that names it, a `RedeemRequest` and a `TwinAcceptance`; `allocations` and `open` read them back by contract id. Last it makes a second account from a second key, has the first send 3 of the test token to it through `TransferFactory_Transfer` (the transfer factory relayed by the service), reads the offer back from `transfers` as the receiver's and as the sender's, has the second account accept it with the accept context the service relays, and checks both accounts' holdings. Then the first sends 2 more that nobody accepts, and the test checks that the receiver cannot withdraw it (404), has the sender withdraw it with the withdraw context the service relays, and checks that the offer is gone for both, the tokens are back with the sender and nothing reached the receiver. The test does not set up a twin (`TwinRules` and `apps/twin/registry`): the twin send and take back are covered by the unit and browser tests, with a manual DevNet check before twin sends are turned on. It prints each prepared transaction, and one topology answer with its key, as fixtures for the explorer (`explorer/src/bridge/canton/fixtures.json`). The local network has no Canton Coin, so it has no faucet to run and no scan proxy: the relay runs against a stand-in for a token registry (`tests/fake_registry.py`, which wants the bearer token the service holds) that serves the test token's rules (an allocation factory, a transfer factory that offers, the accept context), and the test's accept and allocation use what came back through the service. The faucet is tested against a fake wallet in the unit tests only. CI runs both in [`accounts.yml`](../../.github/workflows/accounts.yml).
