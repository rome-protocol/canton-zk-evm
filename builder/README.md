# builder

Makes blocks, gets each one proven and submits it to Canton. Only Canton's commit can finalize the block and determine its order. See [docs/DESIGN.md](../docs/DESIGN.md) ("One block") for the flow. The builder follows the Daml interface in [daml/README.md](../daml/README.md).

One run makes one block (`once`); `run` keeps making them (see "Running it all the time").

## What one run does

In the code a run is three stages, which `_build` composes under `build_block`: `build` (steps 1 to 6, and the start of step 7: it saves the block and its witness and reads the gateway's proofs), `prove` (the rest of step 7: the input tool, the prover and the check of its proof) and `submit` (steps 8 and 9: the `Advance` and the answer). Each can be called alone with the test fakes (`builder/tests/test_stages.py`). One block is in flight at a time.

```sh
python3 builder/builder.py once [--exclude <tx hash>]... [--read-as <party>]... [--disclosed <file>] [--package-id <id>] [--max-block-tx-bytes 65536]
```

1. **Read Canton's head.** It asks the JSON Ledger API v2 for the chain's one active `ZkChain` contract whose `builder` is this builder's party (a chain built by another party, seen through `--read-as`, is not counted): head number, head hash, gas cap, the gateway party and the gateway contract's address. It then moves reth's head, safe and finalized block to that head, so a run after a crash starts clean.
2. **Choose and build.** It reads reth's pending pool (`txpool_content`, on the builder-only WebSocket port) and fills the block by the gas its transactions use, by Ethereum's rule: a transaction fits if the gas used so far plus its own gas limit is at most the block's gas limit. Wallets often declare about three times the gas they use, so counting the declared limits against the cap would stop a block at a third of what it can hold. The builder does not know what a transaction will use until it runs, so reth works it out. The builder takes transactions best price first, each sender's in nonce order, and offers every one that could fit under the lower of the chain's gas cap and the parent's gas limit if each one before it used only 21,000 gas, the least any transaction uses (a transaction named with `--exclude` is left out and ends its sender's turn, because the sender's later ones could not run without it). It fetches the offered transactions' raw bytes in one JSON-RPC batch on the WebSocket (split only if the request would be over the size reth takes). A transaction whose raw bytes come back null (replaced or evicted since the pool was read) is not offered. Two caps apply to what is offered, each in the same way: a transaction that would pass a cap is not offered, and nor are its sender's later ones, so every sender's transactions stay in nonce order and the others go on. The first is the block's raw transaction bytes, `--max-block-tx-bytes` (65,536 by default): our participant spent about 23 ms per KB of the Advance argument in each of its two passes (submission and confirmation) under package 0.1.0, and spends about 3 to 5 ms under package 0.2.0, which DevNet has run since block 1453; at the 0.1.0 cost, a block of 64 KiB of raw transactions makes an argument of about 130 KB, about 6 seconds of its work; a block of 331 KB of argument took 20 to 35 seconds and passed the 20 second JSON API timeout. The code's default stays at 65,536, and DevNet runs 196,608 since 25 October 2026, after the cost per KB fell. The first transaction of a block is always offered, so one bigger than the cap is not left waiting for ever. The second is about 10 MB of raw hex, because reth refuses a WebSocket request over 15 MB. It calls `testing_buildBlockV1` on Canton's head with that list. reth runs the list in order and, with `--testing.skip-invalid-transactions`, leaves out any transaction it cannot run (a gas limit over what the block has left, a wrong nonce, too little balance, a fee under the base fee) together with its sender's later ones, so the block is full by gas used. The list is always explicit; an empty block is `[]`, never null, because a null makes reth fill the block from its pool. The attributes are Prague's: a timestamp from the builder's clock and later than the parent's, the fee recipient, zero `prevRandao` and `parentBeaconBlockRoot`, and `withdrawals: []`.
   - **The check.** The block must hold the offered transactions in the order offered, less some (whatever reth left out), and its gas limit and gas used must be at most the chain's gas cap. A block that is anything else, or a reth that refuses the list (it was started without the flag in "What reth needs"), does not stop the chain: for that block the builder packs by declared gas limits as it did before, taking transactions while their gas limits add up to no more than the cap, and builds that list exactly. That block must be the list asked for, and under the cap, or the run fails. The journal's `built` line and a line on stderr say which way each block was packed.
   - **After a left-out leg (step 6)** the transactions are chosen again from the pool with the larger exclude set, in the same way and under the same caps, and reth builds that list: the gas and bytes the left-out transactions held go to others, so one left-out transaction, however big, never stops the others. The rebuilt block is checked like the first (the offered list in order, less some, under the cap) and its transactions are taken from what reth built.
3. **Make it reth's head.** `engine_newPayloadV4`, then `engine_forkchoiceUpdatedV3` with head = the new block and safe = finalized = Canton's head. Every Engine call carries an HS256 token (`iat` = now) signed with the per-run secret in `jwt.hex`.
4. **Read the block's legs.** The gateway contract writes a `Leg` event for every Canton leg a transaction asks for: a deposit (a claim), a withdrawal or a payment. The builder reads them with `eth_getLogs` for this block, the gateway's address and the `Leg` topic, in log order, which is the order of the gateway's running hash. This is reth's own view. Nothing depends on it being honest: Canton compares what the builder sends with the hash in the proven state.
5. **Find each leg's Canton side.** It looks among the contracts it can see (as the builder, and as every `--read-as` party). Contracts that name another chain, operator, confirmer or gateway are never used.
   - **Deposit:** an active `DepositRequest` with the claim's id and recipient, whose allocation is active and visible, has not passed its settle-before time (by the builder's clock), has the chain's operator as executor, goes from the depositor to the gateway party, is in the instrument of the `GatewayToken` for that EVM token, and is for the amount claimed. Amounts are compared as numbers, in base units: a wrapped token has 10 decimals, as a Canton amount does, so nothing is rounded.
   - **Withdrawal:** a `GatewayToken` for the EVM token, a `WithdrawalAcceptance` of the party named in the withdrawal, and unlocked gateway holdings of the instrument that cover the amount. The holdings used are the largest first, no more than needed; they are the withdrawal's `inputs`. At most one withdrawal of an instrument goes into a block, because a holding made earlier in the same Canton transaction cannot be named in advance.
   - **Payment:** active `DvpTerms` with the payment's id, and its token, payee and amount, whose allocation passes the same checks as a deposit's, going from the terms' `u` to their `v`. The builder does not work out the payment id: it finds the terms by it.
   - An allocation can be executed once. Of two legs that want the same one, the earlier in the block keeps it and the later has no Canton side.
   - If two contracts fit one leg (two requests with one id, say), the first one that passes every check is used.
6. **Build again if a leg has none.** If any leg has no Canton side, the builder leaves out the transaction that recorded it and that sender's later ones, as `--exclude` does, moves reth back to Canton's head and builds again. reth does not return an unwound block's transactions to its pool, so the builder sends them to the pool again after each move back (a transaction the pool already has is no problem) and chooses the next block's transactions from the pool again, with the larger exclude set, exactly as in step 2 (what the left-out transactions held in gas and bytes is refilled by others; reth may also leave out a transaction it cannot run, which waits in the pool). A transaction of the unwound block that the pool refused to take back is still a candidate, with the raw bytes the builder has; if it does not make the rebuilt block it is reported in `lostTransactions`. It repeats until every leg of the block has its Canton side. Nothing has been proven by then. A leg is judged on its own first, and only when every leg passes alone is it checked whether two want the same allocation or holdings, so a transaction that is going to be left out never takes the place of another. A block with no legs needs nothing from Canton beyond the chain contract.
7. **Prove it.** The raw bytes of the block's transactions were written to `kept-transactions.json` in the work folder once reth had built the block, before it became reth's head (which is what drops them from its pool). Each entry carries the block's `number`; the file holds the entries of every block being made, a rebuilt block replaces only its own entries, and a block's entries are removed when Canton has the block or its transactions are back in reth's pool (a file written without numbers is read as one block's entries). The write goes to a temporary file that is flushed to disk and renamed, so the file is whole or absent. The file goes when its last block's entries go; see "A restart in the middle of a block" below. The builder then saves the block and reth's execution witness in a folder of this attempt (`block-<number>/attempt-<process>-<time>`), reads the gateway's two proofs with `eth_getProof` (while the block is reth's tip, before the prover runs), runs `make-input.sh` on the saved files, then the prover command on the input, and the prover writes its output (`out`) in the same folder. Every attempt has a folder of its own and the newest 3 of a block are kept, so a prover or input tool left behind by a killed builder can only write into a folder the next attempt does not read. The builder reads the 1,344-byte wrapped proof the prover leaves, fails if there is none, and reads the block hash the proof's public values commit to. When the proof is accepted its output folder is moved to `block-<number>/out`, so `block-<number>/out/wrapped-proof.hex` is the proof that was submitted. It never submits a proof whose block hash is not this block's: that is a failure, as if the prover had failed.
8. **Submit.** One `Advance` on the `ZkChain` contract, as the builder party, in the formats of `daml/README.md`: `headerHex`, `txsHex`, `proofHex`, the gateway's two proofs (`gatewayAccountNodes` and `gatewayStorageNodes`, from `eth_getProof` for the gateway's account and its `legs[number]` slot at the new block) and `legs`, one for each event in the order of the events. A block with no legs is submitted too, with the gateway's proofs and an empty list: that is how it is shown that the block needs none. `txsHex` is empty (`""`) for a block with no transactions. The header and the transaction list are cut from reth's raw block (`debug_getRawBlock`) as they sit there; the builder checks the header hashes to the block hash. The argument is saved first, as `block-<number>/advance.json` in the work folder, exactly as it is sent.
9. **After Canton answers.** If it committed, `engine_forkchoiceUpdated` with finalized = the new block. If it refused, reth goes back to Canton's head (head = safe = finalized), and the run reports the reason, the hashes of the transactions it chose, and which of them recorded legs. The refused block's transactions are sent to reth's pool again, so the next run looks at them again: an allocation that was withdrawn or an acceptance that was archived is no longer there, so that transaction is left out. A reply that is lost (the connection dropped, a timeout, a 5xx or 408, an answer that is not HTTP or not JSON) says nothing about the block: the command may still commit, and Canton's head, read now, may be the old one. So the builder records the ledger end before it submits, and settles the command by its own command id: it reads the builder user's completions (`POST /v2/commands/completions`) from that offset until the completion with that id shows. (A submit that plainly never reached the command service, a refused connection or an HTTP 401, 403 or 429, has no command to wait for: it is settled at once as not taken.) A completion that succeeded counts as a commit, exactly as an answer would (with its update id and offset). One that failed is a refusal of the block: reth goes back to Canton's head and the transactions go to the pool again. If no completion shows yet, the outcome is not known: the run prints `{"committed": null, "reason": "...", ...}` and leaves reth where it is, because moving it back could undo a block Canton committed. `once` then waits for the command in the same process (it looks again every 2 seconds) and ends with the result of the settled command: 0 and `"committed": true`, or 2 and `"committed": false`, with `"resolved"` saying how (`completion`; `head`, when Canton's head is the block; or `window`). The completion is read again every second (`once`: every 2 seconds) until the command is settled; a read that fails is simply tried again. Canton's head can settle a commit at any time: when it is the block's hash, the block committed (`"resolved": "head"`). It never settles *not committed* by itself, and neither does the builder's clock, because a participant that lags, or reconnects after it confirmed the command, can still commit it later. The window, `CZE_RESOLVE_SECONDS` (300 by default), is counted in Canton's time, not ours: the completions stream carries `OffsetCheckpoint` messages (`value.synchronizerTimes[].recordTime`, in the JSON Ledger API of the pinned Canton 3.6.3 as in its OpenAPI document), and all commands whose time has passed by a checkpoint, with no completion before it, are lost. So a command with no completion is settled as not committed only when the builder's read, from the ledger end it recorded before the submit, has reached a checkpoint whose record time is at or past the time of the submit plus the window (300 s is well over the 60 s a command can still commit in after its ledger time), and the head is not the block. Then the command can no longer change Canton's head, and the head decides (`"resolved": "window"`). Until then nothing is decided, reth is untouched, and the run stays Not known (the participant emits checkpoints periodically; one that is down or lagging only makes the wait longer). The command's deduplication period is not set by the builder (the participant's default is days), so this window is the builder's own. If neither the completions nor the head can be read, or the participant's time has not reached the end of the window, `once` keeps waiting and, when it cannot go on, exits 2 with `"committed": null` and reth untouched. The command is written to `unresolved.json` in the work folder (number, hash, command id, the ledger end, the time, the chain's genesis hash, and the run and attempt of the journal) before it is sent, and only a definite answer removes it: a commit, a refusal, or a failed completion. If the builder is killed or interrupted during the submit, or the record cannot be written (then nothing is sent), no block is rewound under a command that may commit: reth is not moved and the transactions are not put back while the record exists, and the next run (`once` or `run`) settles the command by its command id before it builds or moves reth anywhere. The record also names the chain it was made on (the genesis hash of reth's block 0), and a record from another chain, left behind when that chain was taken down, is refused with a message that names the file (it is not settled, and reth is not moved; remove `unresolved.json` and `kept-transactions.json` if that chain is gone; `network/down.sh --wipe`, and `down.sh` of a network that is not persistent, remove them with the chain). A record that cannot be read, or kept transactions that are damaged, stop the building the same way (the record's block is still waited for). Every block starts from Canton's head: reth is moved there first (head = safe = finalized), never built on reth's own head. After a block that did not commit, the next run sends the block's transactions from `kept-transactions.json` to the pool again (a transaction the pool has, or whose nonce is used, is no problem).

Any other failure after reth moved also moves reth back to Canton's head, and the transactions of the block it made are sent to the pool again. A `Leg` event that cannot be read is such a failure.

A transaction reth will not take back (for any reason other than already having it or its nonce being used) is not in the pool any more. The builder does not let that pass: the report names it in `lostTransactions` (`{transaction, error}`), on the refused, left-out and failure paths alike (and in `once`, also when the block fails after a restart's recovery lost one), and `run` keeps it in the status file.

**A restart in the middle of a block.** Every start moves reth to Canton's head, and reth does not give back the transactions of a block it unwound. So the transactions of a block in the making are on disk (`kept-transactions.json`) from before reth drops them from its pool. At start (and whenever the file is found later, after a fault that cut the putting back short) `run`, and `once`, move reth to Canton's head and send every transaction in the file to the pool again (the entries of every block in it, in block order), then remove the file. If an Advance was in doubt, it is settled by its command id first. When it committed, only its own entries leave the file and reth's head is made final; the entries of the blocks above it are then sent again, as above. When it did not commit, reth goes to Canton's head and the whole file is sent again, in block order. The attempt of the block that was in doubt gets the outcome of its settle (`committed` or `not committed`) and every other attempt the file names, the abandoned ones in the committed case too, gets a `resolved` line with outcome `restarted` in the journal before the file is removed. A transaction of a block Canton did commit has a used nonce and reth says so; that is ignored. One that reth refuses for another reason is named in `lostTransactions`. A line `{"recovered": <count>, "lostTransactions": [...]}` says it was done. A file written before the entries carried numbers still reads, as one block's entries. One check reads the file everywhere: a list in which every entry is an object with a string `hash` and a string `raw` (and an integer `number` when it has one). A file that fails it (not JSON, not valid text, the wrong shape) is moved to `kept-transactions.json.unreadable-<time>`, a name of its own that never replaces an earlier copy, and reported once. A file that exists but cannot be read at all (permission, a disk error), or that fails the check when a block is added to it, put back or cleared, is left where it is, whole: nothing in it is removed or rewritten, and a settle of an Advance in doubt, and the start, fail before reth is moved, so the loop backs off until the file can be read.

Exit status: 0 committed, 2 not committed (refused by Canton, or not accepted because a service failed) or not known (`"committed": null`), 1 any other failure. Every run prints exactly one JSON line on stdout, failures included (a missing setting, an unreadable secret, no `ZkChain` contract or two of them, a reply that is not JSON, a failing prover): `{"committed": false, "error": "..."}` and exit 1. A failure whose move of reth back also failed carries `rewindError` next to the original `error`; a block Canton refused, when that move back fails, keeps Canton's `reason` and carries `rewindError` too.

### The report

The line a run prints when Canton answered (or may have) has these fields besides `committed`:

| Field | What it holds |
|---|---|
| `number`, `blockHash` | the block |
| `transactions` | the transactions in the block (when it committed) |
| `keptTransactions` | the transactions in the block (when it was refused or the outcome is not known) |
| `legs` | how many legs went with the block (when it committed) |
| `legTransactions` | the hashes of the transactions that recorded legs, in the order of the legs |
| `leftOut` | the transactions left out because a leg of theirs had no Canton side, each as `{"transaction": ..., "reason": ...}`. A transaction named with `--exclude` is not listed. |
| `rejected` | with `"committed": false`: `true` if Canton rejected the command (an HTTP 4xx with an error code), `false` if the Ledger API failed (a 5xx, 429, 401 or 403, a lost reply) and nothing committed. `run` treats only the first as a refusal. |
| `reason` | why Canton refused or did not take the block, or why the outcome is not known |
| `proveSeconds`, `advanceSeconds` | how long making the proof's input and proving took, and how long Canton took to answer the `Advance` |

A transaction left out is put back in reth's pool, where it waits. It goes into a later block once its leg has a Canton side, and its sender can replace it. A refusal the builder could not see coming, such as a token registry's own rule, still needs `--exclude` on the next run: the builder does not remember anything from one run to the next.

## What the builder can see

These two options affect visibility only when supplied:

- `--read-as <party>` (repeatable) adds that party to every Ledger API read and to `readAs` of `Advance`. The builder still acts only as itself. This is how a builder hosted by the operator sees the allocations whose executor is the operator.
- `--disclosed <file>` is a JSON list of disclosed contracts, each as the Ledger API takes it (`templateId`, `contractId`, `createdEventBlob`, `synchronizerId`). The list is passed with `Advance` as `disclosedContracts`, for example the contracts of the token registry. A file that is missing or is not a JSON list of objects fails the run before anything moves.

## Which package version Advance runs under

`--package-id <id>` (a package id: 64 lowercase hex digits) is optional. It pins the Daml package version `Advance` runs under. Every `Advance` is submitted with `packageIdSelectionPreference` set to `[<id>]`, so uploading and vetting a newer version of the package never switches the version by itself; the template is still named by package name. Without the flag nothing is sent and Canton picks the highest version that every participant hosting an informee has vetted, as before. The id is recorded as `package_id` in the journal's `built` and `submitted` events (the field is absent when the flag is not set). A malformed id fails the run before anything moves.

## What reth needs

Start reth only with `network/reth/launch.sh`, with discovery off as it always is. The builder relies on these flags, which `launch.sh` passes and checks:

| Flag | Why |
|---|---|
| `--engine.always-process-payload-attributes-on-canonical-head` and `--engine.allow-unwind-canonical-header` | Needed together. Both let reth move its head back to Canton's head on a forkchoice update (reth 2.5.2, `apply_chain_update`), which the builder does at the start of every run and after a block Canton refused. `testing_buildBlockV1` builds on the parent it is given. |
| `--testing.skip-invalid-transactions` | reth leaves out any transaction it cannot run (gas limit over what the block has left, wrong nonce, too little balance, fee under the base fee), and its sender's later ones, in place of failing the build. The builder's check still requires the block to be the offered list in order less some, under the cap. This is what lets the builder fill a block by gas used. Without it the builder still works: it packs by declared gas limits. |
| `--builder.gaslimit <cap>` | Set to the chain's gas cap (`GAS_CAP` in `PINS`, equal to the genesis gas limit), so a block reth builds is never over the cap. |

`launch.sh` also passes `--rpc.eth-proof-window 1`. The builder no longer needs it: it asks for the gateway's proof at the new block only, which is the newest one. It does no harm.

Without the flags in the table the builder's builds or its move back can fail.

## Settings

All from the environment.

| Variable | Meaning |
|---|---|
| `CZE_LEDGER_USER`, `CZE_BUILDER_PARTY`, `CZE_FEE_RECIPIENT` | Required: the Ledger API user, the builder party, the address that gets the block's fees. |
| `CZE_LEDGER_URL` | JSON Ledger API, default `http://127.0.0.1:7575`. |
| `CZE_LEDGER_TOKEN` | Bearer token for the Ledger API, if the participant wants one. It is read once, at start. A token that expires makes every block fail until the builder is restarted, so for `run` use the next setting. |
| `CZE_LEDGER_TOKEN_FILE` | A file holding the token. It is read again on every Ledger call, so a token that is renewed needs no restart. Replaces `CZE_LEDGER_TOKEN` when set. |
| `RETH_WS_PORT`, `RETH_ENGINE_PORT` | Ports of the reth that `network/reth/launch.sh` started, as there (8546 and 8551). |
| `CZE_STATE_DIR` | Where `jwt.hex` is, as for `launch.sh` (default `./state`). Work files go to `$CZE_STATE_DIR/builder` unless `CZE_WORK_DIR` says otherwise. |
| `CZE_GENESIS` | The genesis file given to `make-input.sh` (default `network/genesis.json`). |
| `CZE_MAKE_INPUT_CMD` | Default `prover/make-input.sh`. Called with `<block.json> <witness.json> <genesis.json> <out.bin>`. |
| `CZE_PROVE_CMD` | Default `prover/prove-one.sh`. Called with `<input.bin> <out-folder>`; it must leave `<out-folder>/wrapped-proof.hex`. |
| `CZE_BLOCK_STRATEGY` | The block-cutting strategy for `run`, the same as `--strategy` (default `on_demand`). |
| `CZE_RESOLVE_SECONDS` | How long an `Advance` with no answer may still commit (default 300). It applies to the submits that may not have reached the participant (a timeout, a 5xx or 408, a lost reply); a refused connection, a 401, 403 or 429 is settled at once as not taken. Until it is over only the command's own completion settles it; after it, with no completion, Canton's head does. The window starts on the builder's clock and assumes the clocks agree within a minute: the builder refuses a value below 120, and if Canton's time is more than 30 s ahead of the builder's clock it does not settle by the window, it keeps waiting and the status says why (`waitingToBeResolved.why`). |
| `CZE_TRAFFIC_URL` | Where the builder's participant reports its traffic (a JSON traffic state with `extraTrafficConsumed` and `baseTrafficRemainder`). Empty (the default): the traffic state is not read; the traffic then comes from the completion of the `Advance`, where it carries one (see the journal), and is `null` otherwise. |
| `CZE_SOURCE_COMMIT` | The commit the builder was started from, written to the journal at the start of a run. Default: `git rev-parse HEAD`, else `unknown`. |

The prover is whatever `CZE_PROVE_CMD` runs. By default that is `prove-one.sh`, which sends the input to the prover through ZisK's own remote client, so `ZISK_COORDINATOR_URL` says which prover host. `prove-one.sh` also runs `cargo-zisk verify` on the proof; that check is not made under the pinned keys (`programVK`, `rootC`). The check under the pinned keys is the sidecar's, in Canton's confirmers. Any other command with the same two arguments works, for example a script that copies the input to the prover host over SSH and brings the proof back.

## Running it all the time

```sh
python3 builder/builder.py run [--read-as <party>]... [--disclosed <file>] [--package-id <id>] [--idle-ms 500] [--strategy on_demand] [--gather-ms 0] [--heartbeat-seconds 0] [--test] [--status-file <path>] [--exclude-cooldown-seconds 600] [--max-block-tx-bytes 65536]
```

`run` keeps the chain moving without anyone starting the builder by hand. It reads the same settings as `once` and takes `--read-as`, `--disclosed` and `--package-id` the same way. Each time round it asks reth, on the same builder-only WebSocket port, how many transactions its pool has waiting (`txpool_status`). If there are some, it builds a block with exactly the code `once` runs: from Canton's head, proved, submitted; only that build reads the transactions themselves (`txpool_content`). If the pool is empty it waits `--idle-ms` (at least 50) and looks again, and an idle loop never fetches the pool. With `--heartbeat-seconds N` greater than 0 (the old name `--empty-every-seconds` still works) it also makes an empty block when no block was committed for N seconds, so a quiet chain still shows it is alive. Only that heartbeat ever proves and submits an empty block.

**Only one builder at a time.** `run` and `once` both take an exclusive lock on `builder.lock` in the work folder and refuse to start if another one has it, because two builders would move the same reth and race with their blocks. To make one block by hand while `run` is going, stop `run` first.

**A pool with nothing that can go in.** A transaction can wait in the pool and still not be includable: its leg has no Canton side yet, it is held back, or it does not fit. If a block made for the pool would hold no transaction, the loop does not prove or submit it. reth goes back to Canton's head and the loop looks again a little later: after 2 seconds, then 4, 8 and so on up to 30 seconds while the pool stays the same, and after at most 2 seconds whenever the number of waiting transactions changes. Between two looks the loop does not even count the pool for 2 seconds, and after that it counts (`txpool_status`) and builds from the pool only if the count changed or the pause is over; a replacement with the same count is seen when the pause ends, in 30 seconds at most. The look is cheap: it builds and matches the legs but proves nothing. So a transaction whose leg gets its Canton side later goes in without anything else happening, and a transaction that no one will ever settle (a claim of a deposit nobody made, say) costs no proof and no commit. A line `{"skipped": true, "number": ..., "leftOut": [...]}` says which transactions are left out and why, once for each change.

What it does after a block:

| Outcome | What the loop does |
|---|---|
| Committed (`once` exits 0) | Goes on at once. |
| Refused by Canton (`"rejected": true`) | Waits 1 second, then 2, 4 and so on up to 30 seconds while refusals follow each other; a commit sets it back. The transactions are back in reth's pool, as after `once`. A transaction that was in the kept list of two refused blocks in a row is suspected. If it is the only one both blocks had in common it is left out, as `--exclude` does, for `--exclude-cooldown-seconds` (600 by default), and listed in the status. If there are several, the loop makes one block for each of them in turn, with the other suspects kept out of it, and leaves out the one whose block is refused, so an honest transaction that was only next to a bad one is not held back with it. A left-out transaction is tried again once the cool-down is over. |
| Canton did not take it, and no refusal (`"committed": false, "rejected": false`) | The Ledger API failed, and the command's completion shows that it failed (the synchronizer is disconnected, a service is down, and the like). This is a failure, not a refusal: it backs off like one below, and no transaction is held back for it. A submit that plainly never reached the command service is settled at once as not taken, without waiting: a refused connection (`ConnectionRefusedError`), or an HTTP 401, 403 or 429 (the token or back-pressure turned the call away before the participant took the command, so no completion will ever come). Every other HTTP error that is not a plain rejection (a 5xx, 408, an answer with no error code, or a command id Canton already knows: `DUPLICATE_COMMAND`, `SUBMISSION_ALREADY_IN_FLIGHT`), a timeout and a dropped or unreadable reply are settled by the command's completion like a lost reply: while none shows, the block is Not known (next row). A command id Canton already knows has its first completion before the ledger end the builder recorded, so it too waits for the window. |
| Not known (2, `"committed": null`) | The Advance got no answer and its command has no completion yet. Nothing else is built, reth is not rewound, and the status says `waitingToBeResolved` (`number`, `hash`, `commandId`). On each following round the loop reads the builder user's completions from the ledger end it recorded before the submit, until the completion with the command id arrives or Canton's time is past the window (every second, also when a read fails; a failed read of Canton's head goes through the backoff). A completion that succeeded: the block counts as committed (reth's head is made final). One that failed: reth goes back to Canton's head and the block's transactions are sent to its pool again, so they go into a later block. No completion, and Canton's own time (an `OffsetCheckpoint` of the completions stream) is past `CZE_RESOLVE_SECONDS` (300 by default) after the submit: the command can no longer commit, and Canton's head decides. Canton's head showing the block settles a commit at once. A line `{"resolved": "committed" or "not committed", "number", "blockHash", ...}` says which, with `updateId` and `completionOffset` for a commit (null when the head decided), and the journal's `resolved` line says how (`via`) and carries `update_id` and `completion_offset` too. `once` that settles an earlier run's block this way before it builds prints that block's outcome as `settledEarlier` (`number`, `blockHash`, `commandId`, `committed`, `resolved`, `updateId`, `completionOffset`) in its own line. A restart settles the command first, from `unresolved.json`. A transaction that reth would not take back is named in `lostTransactions` of that line and of the status. Until then reth's `latest` is a block that Canton may never have committed, so the explorer shows it as being proven. |
| The input tool or the prover failed (`error`), or the prover gave a proof of another block | A failure, with the backoff below, and the transactions are back in reth's pool. Once is taken for a service that is down. If the next block fails the same way and has a transaction in common with the one before, the loop looks for the culprit so that one transaction the prover cannot finish never stops the chain. A single common transaction is left out for the cool-down. Several are narrowed down by halves: the loop makes a block with half of them (the other half and the ones already cleared kept out), and one whose block fails is narrowed again, until one is left; a half whose block gets through is cleared, and a lone candidate is tried alone before it is blamed. If the failure goes away while this goes on, nobody is blamed and the hunt ends. Nobody is blamed until a block has passed the input tool and the prover since the failures began, so a prover that is down for a while never costs an honest transaction its place: if no block has passed, the loop first makes a block without the candidates (an empty one if need be), and if that fails too, the count starts again. The culprit is left out for `--exclude-cooldown-seconds`, doubled each time the same transaction is convicted again (up to a day), said in a line `{"excluded": ..., "until": ..., "reason": ...}`, and listed with its reason in the status. |
| Any other failure (1), or a pool that cannot be read | Waits 1 second, then 2, 4, 8 and so on up to 30 seconds while it keeps failing, and tries again, with no end to the trying. A block that is answered sets the wait back to 1 second. |

A refused block and a failed block do not count as two in a row for the leaving out. Only two refusals next to each other do. A suspect that was held back wrongly (for example, a new bad transaction came into the block of its trial) is tried again when its cool-down ends.

One JSON line goes to stdout for every block, the same report `once` prints (a failure prints `{"committed": false, "error": "..."}`, with `rewindError` next to `error` when the move of reth back failed too), so it can be followed with `tail -f` or sent to a log collector. A stdout that is closed does not stop the loop.

**Stopping.** `SIGTERM` or `SIGINT` (Ctrl-C) finishes the block in progress, writes the status, and exits 0. The input tool and the prover run in their own session, so a Ctrl-C at the terminal, which reaches the whole process group, does not cut a proof short. A second signal acts as it usually does. A block cut off in the middle is the same as after a crash: the next start goes back to Canton's head. Run it under a service manager that restarts it, and it is safe to restart at any time. A service manager that signals every process of the service when it stops must be set to signal the builder first and the rest only at the end (for a Linux init system: a kill mode of `mixed`), and its stop timeout must be longer than a proof and the Canton answer put together, or it will end a block in progress. Set it to restart the builder after any exit.

**Work folders.** Every block keeps `block-<n>` in the work folder: `out` (the proof), `advance.json`, and one `attempt-<process>-<time>` folder for each of the last 3 attempts (block, witness, input). `run` removes the folders of committed blocks that are more than 10 behind the newest one. `once` removes none of that, but, like `run`, it keeps only the newest 3 attempt folders of the block it builds.

**The status file.** `--status-file` (default `status.json` in the work folder) is JSON, replaced atomically by the loop at start, after every block or look that finds nothing it can include, every 5 seconds while idle, after a failure, while it waits for an unresolved block or cannot read an in-doubt record, and at stop (with the final state). Between those writes a small background ticker refreshes `updatedAt` every few seconds, so a long block (a slow proof or Advance) does not make the file look stale. It does so only while the loop's last write is less than 300 seconds old, so a stuck step goes stale and a monitor sees it, and a quiet chain does not. `updatedAt` shows the producer process is alive:

| Field | What it holds |
|---|---|
| `state` | `running`, `stopped` (a signal) or `crashed` (anything else ended it) |
| `runId`, `journalError` | the run's id in the journal, and `{time, error}` of the last journal write that failed (`null` if none) |
| `startedAt`, `updatedAt` | UTC times |
| `lastCommitted` | `{number, hash, time}` of the last committed block, or `null` |
| `blocksCommitted`, `blocksRefused`, `blocksUnknown` | counts since the loop started |
| `consecutiveFailures` | failures since the last answered block |
| `lastError` | `{time, error}`: the last refusal reason, unknown outcome or failure. If moving reth back after the failure or the refusal failed too, `error` is still the original and `rewindError` holds the second |
| `excluded` | the transactions left out now, each as `{transaction, until}`, and `reason` for one the prover could not finish |
| `searchingForUnprovable` | `{candidates}` while the loop looks for a transaction the prover cannot finish, else `null` |
| `waitingToBeResolved` | `{number, hash, commandId}` of a block whose Advance got no answer and has no completion yet, or `null` |
| `lostTransactions` | transactions that could not be put back in reth's pool after a block that did not commit or a restart, each with the error and the time (the last 100) |
| `averageProveSeconds`, `averageAdvanceSeconds` | averages over the blocks that were proven, or `null` before the first |

A status file that cannot be written is reported once on stderr (again after a write has worked in between) and does not stop the chain.

## The block-cutting setting

`run` takes `--strategy` (or `CZE_BLOCK_STRATEGY`). There is one strategy now, and it is the default:

| Strategy | When a block is cut | Parameters |
|---|---|---|
| `on_demand` | When at least one transaction that can go in waits and no block is in flight (one block at a time is in flight). With `--gather-ms`, the producer waits that long after the first transaction reaches an empty pool, so a few more can share the block. A pool that is still busy after a block is cut at once (`pool`): a busy chain batches by itself. | `--gather-ms` (default 0: cut at once), `--heartbeat-seconds` (default 0: never an empty block; `--empty-every-seconds` is the old name) |

The producer refuses to start with a setting that cannot keep up, and says why: an unknown strategy, a negative number, a `--gather-ms` over 30,000 (a transaction would wait longer than a block takes), or a heartbeat shorter than an empty block takes to prove (6.3 s measured on the testnet's prover). `--test` marks the run in the journal as a flood or another test, so the explorer's statistics can leave it out.

## The journal

`run` appends one JSON line per event to `journal/YYYY-MM-DD.jsonl` in the work folder (`CZE_WORK_DIR`, by default `builder` in the state folder; the file of the line's own UTC day, so a new day is a new file). Each line is flushed and synced to disk, and so is the folder when a new file is made. Every line has `v` (the format version, 1), `run` (the run's id), `seq` (a number that starts again with every run, so (`run`, `seq`) is a line's key and a reader's place in the journal is the file and the byte offset) and `time` (UTC, in milliseconds). A line cut short by a crash is ended with a newline before the next one is written.

A journal that cannot be written never stops the chain. The failure is in the status file (`journalError`: `{time, error}`, `null` once a write has worked again), the line is lost, and the next line tries again. A lost line leaves a gap in `seq`.

**Per block attempt** (every line has `attempt`, the attempt's number in the run):

| Event | When | Fields |
|---|---|---|
| `cut` | the producer decides to build | `number` (Canton's head plus one), `strategy`, `cut_reason` (`pool`, `gather`, `heartbeat`, `retry` or `probe`), `pool_waiting`, `idle_before_cut_ms`, `in_flight_at_cut` |
| `built` | reth has made the block its head and the legs are matched | `block_hash`, `parent_hash`, `tx_hashes` in order, `gas_used`, `legs`, `rebuilds`, `left_out` (each with its reason), `packed` (how the block's last build, the one that went on, chose its transactions: `gas_used`, or `gas_limits` when the builder fell back, with `pack_reason`), `offered` (how many transactions reth was offered), `tx_bytes` (the raw bytes of the block's transactions), `max_tx_bytes` (the cap in force, `--max-block-tx-bytes`), `package_id` (only with `--package-id`) |
| `skipped` | a build with no transaction that can go in (the attempt ends) | `left_out`, `rebuilds` |
| `proof_queued`, `proof_started`, `proof_ended` | around the prover | `prover`; on the end `outcome` (`ok`, `failed` or `wrong_block`), `seconds`, and for a block that did not prove, `reason` (the first 300 characters of the error) |
| `submitted` | just before `Advance`, and after the in-doubt record is on disk (see below) | `command_id`, `argument_bytes` (the size of `advance.json`), `package_id` (only with `--package-id`) |
| `answered` | Canton answered, or did not (the attempt ends) | `outcome` (`committed`, `refused`, `not_taken`, `unknown`, or `failed` when reth, the ledger or the prover failed it first, with `stage`), `reason`, `update_id` and `completion_offset` (from the submit-and-wait answer; `null` after a lost reply), `seconds`, `traffic_bytes`, `traffic_before`, `traffic_after` |
| `resolved` | an unknown outcome was settled later | `outcome`: `committed` or `not committed`, `via`: `completion` (the command's own completion), `head` (Canton's head is the block) or `window` (none came before Canton's time was past the window, so Canton's head decided), and for a commit `update_id` and `completion_offset` when its completion showed them; after a restart, with `attempt_run` (the run that made the attempt) `restarted` (in the next run, with `attempt_run`) is for a block cut short with no command in doubt, or one above the block whose command was in doubt |
| `final_seen` | reth's finalized block moved to the block | `number`; after a restart, with `attempt_run` as `resolved` has it |

The command id is `ostia-<chain id>-<number>-<first 16 hex of the block hash>-<attempt>`, the same for the same block and attempt. `once` uses one too. The update id is the same on every participant, so it joins the producer's attempt to the reader's update. `traffic_bytes` is what the builder's participant used across `Advance` (from `CZE_TRAFFIC_URL`): the extra traffic consumed after minus before, plus what the free base allowance covered first (`baseTrafficRemainder` before minus after, if it dropped). A refill of the allowance during `Advance` makes it a little low, so the `answered` line also carries the raw `traffic_before` and `traffic_after` (`extra_consumed`, `base_remainder`, `timestamp`) for the loader to work it out exactly. It is read only while no other block is in flight, and it is `null` where the participant does not report both fields, does not answer, or the consumed counter went down. A traffic read waits at most one second, and after one that timed out the participant is left alone for a minute, so a participant that hangs costs a block at most once a minute. A traffic read that fails for any reason (a token file that cannot be read, say) never changes the outcome of a block that Canton committed. Where the traffic state gives none (a participant on the Canton Network's DevNet has no traffic-state URL, so `CZE_TRAFFIC_URL` stays empty), a committed block's `traffic_bytes` is the `paidTrafficCost` of its completion instead: the traffic the participant paid for the confirmation request. The builder reads that one completion (`POST /v2/commands/completions` at the offset the submit-and-wait answer gave, for the builder's user and party, with a short idle timeout), matches the command id, and also puts the number in the block report as `trafficBytes`. That read is the command's own, so it is made whether or not another block is in flight; the raw `traffic_before` and `traffic_after` stay `null`. A read that fails or finds no completion leaves `traffic_bytes` `null` and never fails the block. The `answered` line is stamped with the time Canton answered, taken before this read and the traffic reads, so the read's duration (about a second while the completions stream waits out its idle timeout) never shows in the line's `time`. A completions read that times out is not tried again for a minute, as with the traffic read.

**The in-doubt record.** Before it sends the `Advance`, the builder writes `unresolved.json` in the work folder, and the `submitted` line follows. The record holds the block's number and hash, the command id, the ledger end read before the submit (`begin`), the submit time, the genesis hash of reth's block 0, and the `run` and `attempt` of the journal. It is removed only when the command is settled: a commit, a refusal, a failed completion, or a submit that never reached the command service. After a lost reply the builder reads the command's completion first. If it finds a completion, the builder clears the record and writes an `answered` line that says `committed` for a success and `not_taken` for a failure. If no completion is found at once, the record stays and the `answered` line says `unknown`. Step 9 above explains how the builder then decides whether the command committed: it reads the completions from `begin` until the completion with the command id shows or the `OffsetCheckpoint` record time is past the submit time plus `CZE_RESOLVE_SECONDS`. A run that settles it writes `resolved` (for either outcome) and, for a commit, `final_seen`. Both carry `attempt_run` when the attempt was an earlier run's.

**Who reads it.** The explorer's indexer reads `journal/` and `status.json` from the work folder, read only (`JOURNAL_DIR`, `PRODUCER_STATUS_FILE`; `explorer/run.sh` mounts the folder with `:ro`), and loads the lines into its lifecycle tables. The builder is the only writer. `network/restart.sh` and `network/sync_reth.py` do not read the journal. They read `unresolved.json` through the builder's own `recover_saved`, with `builder.lock` held, so a running builder is refused. If a record is there, they settle the command by its command id first, as above, and only then compare reth with Canton's head. Settling clears `unresolved.json` and `kept-transactions.json`, and writes no journal line. So an attempt that `restart.sh` settled keeps its `answered` line with `outcome` `unknown` and gets no `resolved` line; the indexer settles that attempt as committed when its block hash is an indexed block (`explorer/server/indexer/journal.ts`). `sync_reth.py` prints the command id, whether it committed and how it was settled (`in_doubt_command`, `in_doubt_committed`, `in_doubt_resolved`).

**A failure before Canton's head is read** (reth's WebSocket or the ledger is down) has no block number, so it is not a block attempt: the producer writes `attempt_failed` (`attempt`, `stage`, `reason`, and the cut's `strategy`, `cut_reason`, `pool_waiting`, `idle_before_cut_ms`, `in_flight_at_cut`) and no `cut` or `answered`. The loader keeps these out of the block attempts.

**After a restart:** an attempt that was cut short when the producer stopped, with no command in doubt (or one of the blocks above a block whose command was in doubt), has no `answered` line. The next run gives the transactions back to reth and writes `resolved` with `outcome` `restarted`, `attempt` and `attempt_run` (the run of that attempt). It does not say whether Canton took the block: the loader joins the attempt's `built` line to the block hash that Canton's head shows. An attempt whose Advance had no answer has an `answered` line with `outcome` `unknown` and a record in `unresolved.json`: the next run settles it by its command id and writes `resolved` (`committed` or `not committed`, with `via`) and, for a commit, `final_seen`, both with `attempt_run`, so they belong to the attempt of the earlier run.

**Per run:** `run_started` (`strategy`, `settings`, `source_commit`; the settings include `test`), `pool` (`waiting`: reth's count of waiting transactions, at most once a second and only when it changes), `excluded` (a transaction left out, until when, and why), `lost` (transactions reth would not take back, once for each time) and `run_stopped` (`state`).

Per transaction, `built` says which transactions the block holds, and `answered` with `committed` says they are final.

## Not here

- No check of the proof under the pinned keys before submitting it; the builder checks only its size and form. Canton's confirmers check it.
- No step cap before proving. A prover that never returns stops the loop: the loop finds a transaction the prover fails on, not one it waits on forever, so `CZE_PROVE_CMD` needs a timeout (the default `prove-one.sh` has `--timeout ${CZE_PROVE_TIMEOUT:-1800}`).
- `once` makes one block. The loop is `run`.
- If the process dies in the middle of a block, the next start goes back to Canton's head and sends the block's transactions to the pool again from the file written before proving. The file is written before reth drops the transactions from its pool, so there is no moment at which they are in neither place. A disk that cannot be written stops the block, and the transactions stay in the pool.
- No memory from one `once` to the next. A refusal for a reason the builder cannot see (a registry's own rule) is handled by `run` after two refusals in a row, or by hand with `--exclude` when using `once`. `run` keeps its list of left-out transactions, and what it has learned about a transaction the prover cannot finish, in memory only: a restart forgets it, and a transaction that cannot be proven is found again after two failures.
- The builder cannot see everything about a leg. It judges the settle-before time by its own clock, and an allocation can be withdrawn between its check and the commit. Then Canton refuses the block, nothing moves, and the next run sees the allocation is gone.
- The builder needs read access to the contracts of the legs it settles: the requests, tokens, acceptances, terms, allocations and the gateway's holdings. This repository uses `--read-as` to give it the view of the parties that hold them. A deployment must grant that access; a leg whose contracts the builder cannot see has no Canton side, and its transaction is left out.
