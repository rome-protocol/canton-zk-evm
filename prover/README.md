# prover

Scripts that run the ZisK prover for this guest on the GPU machine. Machine hosting, creation and deletion are outside this repository's scope. `ZISK_COORDINATOR_URL` selects the coordinator and defaults to the one on the same machine.

The supplied installer targets Linux x86-64 with `apt`, `sudo`, an installed NVIDIA driver and about 100 GB of free disk. It installs system packages and changes memory-lock limits. See [docs/METRICS.md](../docs/METRICS.md#the-machine) for the tested hardware and memory measurements. Minimum GPU memory for the whole prover is not established here.

| Script | What it does |
|---|---|
| `install.sh` | Installs the ZisK release in `PINS` (GPU build; `ZISK_CPU_ONLY=1` for the CPU build on a machine with no GPU), its Poseidon1 proving key and our PLONK key. It checks the installer, the Rust toolchain archive, the release binaries and the proving key against their SHA-256 in `PINS` before it installs them, every installed proving-key file against `zisk-<version>-keys.sha256` afterwards, and the five files of our PLONK key against `PINS` (see "The release files" and "Our PLONK key"). |
| `build-plonk-key.sh` | Builds our PLONK key from ZisK's Poseidon1 proving key and the pinned ptau, with the Node packages from a lock file (see "Our PLONK key"). `install.sh` runs it when it has no copy of the key. |
| `build-guest.sh` | Copies the guest sources into one fixed folder (`/tmp/cze-guest-build`), builds the guest ELF there, and prints its SHA-256, programVK, rootC and the rules hash. It takes an optional genesis file in place of `network/genesis.json`, for a chain whose Osaka fork starts later than genesis. The folder you run it from does not change the ELF: two fresh checkouts gave the same programVK on real ZisK (see `guest/README.md`). It stops if the ELF still holds a build path. `guest-env.sh` has what it uses for that. Run one build at a time: the folder is emptied at the start of each. |
| `start.sh` | Starts the coordinator and one GPU worker with the final SNARK key (ours, PLONK) loaded (`--snark --preload-snark`), and leaves them running. |
| `prove-one.sh` | Proves one input, verifies the proof with `cargo-zisk verify -k final.verkey.json` (the trusted key, checked against `PINS`), and writes the 1,344-byte wrapped proof as hex. |
| `make-block.py` | Makes one block with one transfer on a temporary copy of the chain, through reth's testing and Engine APIs, and saves the block and its execution witness. |
| `make-input.sh` | Turns that block, its witness and the genesis into the prover input, using zisk-eth-client's own input code. |

## The Rust toolchain

ZisK's installer installs the Rust toolchain with `cargo-zisk toolchain install`, which takes the highest `zisk-4.x.y` release of 0xPolygonHermez/rust that exists, so the toolchain it installs changes when a release is published there (it asked for `zisk-4.1.0` before that release had any files, and the install stopped on a 404). `install.sh` therefore downloads the release named by `ZISK_TOOLCHAIN` in `PINS` (`zisk-4.0.0`), checks the archive against `ZISK_TOOLCHAIN_SHA256`, and gives it to the installer through `ZISK_TOOLCHAIN_SOURCE_DIR`. `PINS` pins `zisk-4.1.0`, the toolchain ZisK 1.4.0's installer takes (the pin was `zisk-4.0.0` for 1.3.2; the toolchain is part of what the guest ELF and so its programVK come from). Moving to another toolchain release is a change to those two lines of `PINS`, and the guest is rebuilt and its programVK checked afterwards.

## The release files

ZisK's installer, `ziskup`, checks each key it downloads only against an md5 file that sits next to it in the same bucket, and it does not check the binaries. That finds a broken download, not a changed file. So `install.sh` downloads the files itself (the release binaries `cargo_zisk_linux_amd64.tar.gz` and the Poseidon1 proving key `zisk-provingkey-<version>-poseidon1.tar.gz`; also `ziskup` and the Rust toolchain archive, which `PINS` already pins), checks each against its SHA-256 in `PINS` (`ZISK_RELEASE_SHA256`, `ZISK_STARK_SETUP_SHA256`), and only then lets `ziskup` install them, from a copy of `ziskup` whose two download addresses point at the folder that holds them (`zisk-artifacts.sh`; `tests/zisk-artifacts.sh` checks that the copy differs from the pinned `ziskup` in those two lines and nothing else). After the install it checks every file the proving key unpacked against `zisk-<version>-keys.sha256`, a list taken from the checked tarball; the files ZisK generates next to them later, such as the constant trees, are not in it.

`ZISK_ARTIFACTS_DIR` names a folder for the files (`ziskup`, the toolchain archive `rust-toolchain-x86_64-unknown-linux-gnu.tar.gz`, the release binaries, the proving key, and a kept copy of our PLONK key as the folder `provingKeySnark/`). A file already there with the pinned checksum is used without a download, so a kept copy installs without ZisK's GitHub and its setup bucket; files with another checksum are downloaded again and checked. The installer still fetches the system packages, `rustup` (only when `cargo` is missing), Node (at `NODE_VERSION`, by its SHA-256) and the Node packages from the lock file. Without it they go to a folder under the prover state and are deleted after the install. The proving key is about 5 GB, and `ziskup` copies it once more before it unpacks it. `ZISK_SNARKJS_LINK` names where the `snarkjs` link goes (default `/usr/local/bin/snarkjs`), for a machine that keeps another ZisK install beside this one.

## Our PLONK key

ZisK 1.4.0 publishes no PLONK key, and its `setup_snark` installs a pilfflonk key, whose proofs are 6,752 bytes and have no Rust verifier here. We keep the PLONK wrap (1,344 bytes, the verifier crate), so `build-plonk-key.sh` builds the key: ZisK's own `cargo-zisk-dev proofman-setup setup-snark --final-snark plonk` on the installed Poseidon1 proving key (a blake3 key takes pilfflonk only), the pinned powers-of-tau file (Hermez final_24, `ZISK_PTAU_BLAKE2B` and `ZISK_PTAU_SHA256`, 19 GB, downloaded over HTTP/1.1 because circom.info drops long HTTP/2 transfers) and `prover/plonk-key/publics.json` (ZisK's `state-machines/publics.json` at `ZISK_COMMIT`, `ZISK_PUBLICS_INFO_SHA256`). It needs about 60 GB of disk, 16 GB of RAM and, on the machines tried, 15 to 25 minutes (the C++ witness library of the final circuit takes most of it).

The setup's Node tools (pil2-compiler, snarkjs, circomlib) are installed from `prover/plonk-key/package-lock.json` with `npm ci --ignore-scripts` (pil2-compiler by a full commit hash, the rest by integrity hash), and the finished tree is checked against `PLONK_NODE_TREE_SHA256`. ZisK's own setup would run `npm install` with no lock file and take whatever the registry and the pil2-compiler branch hold that day. The setup is pointed at that tree (`PIL2C_EXEC`, `SNARKJS_PATH`, `CIRCOMLIB_PATH`) and `npm` is replaced for its run by a stub that stops, so nothing is fetched; where `sudo` and `unshare` exist it also runs in an empty network namespace, so that nothing can be.

The setup is deterministic: the same inputs gave byte-identical key files on two machines. Five files are pinned by SHA-256 in `PINS` (`ZISK_PLONK_FINAL_ZK_SHA256`, `ZISK_PLONK_FINAL_VK_SHA256`, `ZISK_PLONK_VERIFIER_SHA256`, `ZISK_VADCOP_FINAL_VK_SHA256`, `ZISK_RECURSIVEF_VK_SHA256`): `final/final.zkey` (the proving key, 25.9 GB), `final/final.verkey.json` (the key `cargo-zisk verify -k` takes), `final/PlonkVerifier.sol` (whose eight commitments are `vk::ZISK_1_4_0` in the verifier crate), `vadcop_final.verkey.json` (the rootC every proof carries) and `recursivef/recursivef.verkey.json`. The script and `install.sh` stop if any of them differs. The compiled witness libraries (`final.so`, `recursivef.so`) and the other files of the folder are not pinned: a proof depends on the five, and a wrong witness library can only make a proof fail.

## The wrapped proof

1,344 bytes: the PLONK proof (768), the programVK (32), rootC (32) and the public values (512), one after the other. `prove-one.sh` writes them as `wrapped-proof.hex` and as the JSON that `cargo-zisk-dev export-solidity-calldata` makes.

## Why `make-input.sh` is not zisk-eth-client's `input-gen`

`input-gen` reads a block from an RPC node over HTTP and refuses any chain it does not know. Ours is not one of them, and reth's debug API is not on our HTTP port. `make-input.sh` builds a small program against the same input code at the same pinned commit and gives it the block, the witness and the chain config as files.

## Fixtures

`fixtures/` holds a one-transfer block's GPU proof and its recorded details (see `session.txt`), and the block itself (`block1.json`: its hash, its header and its transaction list as they sit in the block's own encoding, for the full-pass tests of the sidecar and the explorer's check). This is public data. `tests/fixtures.sh` checks its consistency.

## The ZisK release

`PINS` pins ZisK 1.4.0-alpha (commit `64a1f1664184e76053686745d50c6b9aaa51b034`). ZisK no longer patches 1.3.2, and 1.4.0 has soundness fixes (see [SECURITY.md](../SECURITY.md)). The guest is zisk-eth-client v0.14.0 with our chain rules and the dependency updates described in `guest/README.md`, built with the `zisk-4.1.0` toolchain. The fixture is the proof of that guest, proven under 1.4.0 with our PLONK key, and `session.txt` records its program key and root. It also keeps `previous_programVK` (the guest of the DevNet-genesis build under ZisK 1.3.2, key B of the running chain) and `previous_rootC`, which the older demo results and the program-switch tests refer to. A new chain's sidecars and explorer are pinned to the keys in `session.txt` and to ZisK 1.4.0. A chain that runs on 1.3.2 and switches to 1.4.0 keeps its old key for its old blocks (`sidecar/README.md`, "A short list of keys", and `network/README.md`, "Switching a running chain").
